# Техническое задание: Foundly

Сервис поиска потерянных и найденных вещей в университете.

Версия: 2.0 (расширенная: роли, AI-агенты, матрица возможностей, командная работа)

## 1. Цель проекта

Создать веб-сайт, где студенты и сотрудники университета публикуют объявления о потерянных и найденных вещах, быстро находят нужное по фильтрам и связываются с автором объявления. Все пользователи видят единую общую ленту.

Проект учебный и портфолио-ориентированный: демонстрирует fullstack-разработку на Next.js с облачной базой данных, авторизацией, хранилищем файлов и архитектурой, готовой к подключению AI-агентов.

## 2. Проблема

Потерянные вещи (ключи, наушники, студенческий, зарядки, одежда) ищут через разрозненные чаты и объявления на стенах. Информация теряется, нет единого места, статуса поиска и никто не отвечает за порядок в объявлениях.

## 3. Целевая аудитория

- Студенты университета (основная группа)
- Преподаватели и сотрудники
- Администрация и охрана (находят вещи в корпусах)

## 4. Роли пользователей системы

| Роль | Кто это | Что может |
|---|---|---|
| Гость | Любой посетитель без входа | Смотреть ленту, искать, фильтровать, открывать объявления |
| Пользователь | Вошедший студент или сотрудник | Всё, что гость, плюс создавать объявления, менять статус и удалять *свои* объявления, смотреть «Мои объявления» |
| Модератор | Назначенный сотрудник или студент | Всё, что пользователь, плюс скрывать чужие объявления и просматривать жалобы |
| Администратор | Владелец сервиса | Всё, что модератор, плюс назначать роли, удалять любые объявления, управлять категориями |

Роль хранится в таблице profiles (поле role). Права проверяются на уровне базы данных (RLS), а не только в интерфейсе.

## 5. AI-агенты (этап 2, архитектурная заготовка)

В первой версии AI не подключается. Но структура данных и права проектируются так, чтобы агентов можно было добавить без переделки проекта. Каждый агент это отдельный сервисный аккаунт со своей ролью и ограниченными правами.

| Агент | Роль | Задача | Может | Не может |
|---|---|---|---|---|
| Агент-модератор | Помощник модератора | Проверять новые объявления на спам, оскорбления, запрещённое содержимое | Ставить пометку «на проверку», писать причину в журнал | Удалять объявления, блокировать пользователей |
| Агент-сопоставитель | Поисковый помощник | Сравнивать «потерял» и «нашёл» по описанию, категории, месту и дате, предлагать вероятные совпадения | Создавать подсказку «возможное совпадение» для обеих сторон | Менять статус, раскрывать контакты |
| Агент-координатор | Управляющий процессом | Напоминать авторам обновить статус, собирать статистику возвратов | Отправлять напоминания, формировать отчёт для администратора | Менять и удалять объявления |
| Агент-помощник | Поддержка | Отвечать на вопросы «как опубликовать», «что значит статус» | Отвечать по инструкции сайта | Видеть чужие личные данные |

Принципы работы агентов:
- *Человек принимает решения.* Агент только предлагает и помечает, окончательное действие (скрыть, удалить, заблокировать) выполняет модератор или администратор.
- *Минимальные права.* Каждому агенту разрешены только перечисленные действия, остальное запрещено политиками RLS.
- *Журналирование.* Каждое действие агента записывается в таблицу agent_logs (кто, что, над каким объявлением, когда, причина).
- *Отключаемость.* Любого агента можно выключить настройкой без остановки сайта.
- *Приватность.* Агенты не получают Telegram-ники и данные аккаунтов, если это не нужно для задачи.

## 6. Матрица возможностей

| Возможность | Статус | Комментарий |
|---|---|---|
| Лента, поиск, фильтры, статусы | MVP | Основа проекта |
| Регистрация и вход по email | MVP | Supabase Auth |
| Объявления с фото | MVP | Supabase Storage |
| Связь через Telegram | MVP | Ссылка на профиль, без внутреннего чата |
| Роли: пользователь, модератор, администратор | MVP | Поле role и политики RLS |
| Жалоба на объявление | MVP | Кнопка «Пожаловаться», запись в таблицу reports |
| Автоматическая проверка объявлений на спам | Этап 2 | Агент-модератор, требует доступ к LLM API (ключ, расходы) |
| Подсказки «возможное совпадение» | Этап 2 | Агент-сопоставитель, по тексту реализуемо, по фото с ограниченной точностью |
| Напоминания и отчёты | Этап 2 | Агент-координатор, нужны email-рассылка или Telegram-бот |
| Чат-помощник на сайте | Этап 2 | Агент-помощник |
| Карта корпусов | Этап 2 | Нужны данные о корпусах |
| Вход через университетскую почту | Этап 2 | Зависит от политики университета |
| Внутренний чат между пользователями | Этап 2 | Нужен realtime, отдельный объём работы |
| Гарантия возврата вещи | Не реализуется | Сервис связывает людей, но не контролирует передачу |
| Автоматическая проверка, что вещь действительно принадлежит заявителю | Не реализуется | Невозможно без интеграции с университетом и вмешательства человека |
| Полностью автономные агенты без участия человека | Не реализуется | Противоречит принципу контроля, риск ошибок и злоупотреблений |
| Распознавание любой вещи по фото с высокой точностью | Не реализуется | Результат всегда приблизительный, только как подсказка |

## 7. Функциональные требования (MVP)

### 7.1. Авторизация и роли
- Регистрация и вход по email и паролю (Supabase Auth)
- Выход из аккаунта
- Просмотр ленты доступен без входа
- Создание, изменение и удаление своих объявлений только для вошедших
- Роль по умолчанию при регистрации: «Пользователь»
- Назначение модераторов выполняет администратор

### 7.2. Лента объявлений
- Список карточек: фото, название, категория, место, дата, статус
- Адаптивная сетка: несколько колонок на компьютере, одна на телефоне
- Сортировка: сначала новые
- Скрытые модератором объявления в ленте не показываются

### 7.3. Создание объявления
Форма с полями:
- Тип: «Потерял» или «Нашёл» (обязательно)
- Название вещи (обязательно)
- Категория (обязательно)
- Описание
- Место: корпус или аудитория (обязательно)
- Дата (по умолчанию сегодня)
- Фото (загрузка файла, до 5 МБ, форматы jpg, png, webp)
- Telegram-ник (обязательно): латиница, цифры и подчёркивание, от 5 до 32 символов; ссылка формируется как https://t.me/<ник> без символа @

Валидация: пустые обязательные поля не пропускаются, показывается понятная ошибка.

### 7.4. Фильтры и поиск
- Поиск по названию
- Фильтры: категория, тип, статус, дата (сегодня, неделя, всё время)
- Кнопка «Сбросить фильтры»

### 7.5. Статусы
- *Ищется* (по умолчанию)
- *Найдено*
- *Возвращено*

Менять статус может автор объявления. Статус отображается цветным бейджем.

### 7.6. Страница объявления
- Полная информация и большое фото
- Кнопка «Связаться в Telegram»
- Кнопка «Пожаловаться»
- Для автора: смена статуса и удаление
- Для модератора и администратора: кнопка «Скрыть»

### 7.7. Мои объявления
- Список объявлений текущего пользователя

### 7.8. Модерация
- Страница /moderation (для модератора и администратора): жалобы, скрытые объявления
- Действия: скрыть, вернуть, закрыть жалобу

### 7.9. Администрирование
- Страница /admin (для администратора): список пользователей, назначение ролей

## 8. Категории вещей

Документы и карты, ключи, электроника, одежда, сумки и рюкзаки, книги и тетради, другое.

## 9. Структура страниц

| Путь | Назначение | Доступ |
|---|---|---|
| / | Лента, поиск, фильтры | Все |
| /item/[id] | Страница объявления | Все |
| /about | О проекте | Все |
| /login, /register | Вход и регистрация | Гость |
| /add | Новое объявление | Пользователь и выше |
| /my | Мои объявления | Пользователь и выше |
| /moderation | Жалобы и скрытые объявления | Модератор и выше |
| /admin | Пользователи и роли | Администратор |

## 10. Модель данных

Таблица items:

id          — uuid, первичный ключ
user_id     — uuid, автор (auth.users)
type        — "lost" | "found"
title       — название
category    — категория
description — описание
place       — место
date        — дата
image_url   — ссылка на фото
telegram    — ник автора
status      — "searching" | "found" | "returned"
hidden      — boolean, скрыто модератором
created_at  — дата создания


Таблица profiles:

id          — uuid, равен id пользователя
role        — "user" | "moderator" | "admin"
created_at  — дата создания


Таблица reports:

id          — uuid
item_id     — объявление, на которое жалоба
user_id     — кто пожаловался
reason      — причина
resolved    — boolean
created_at  — дата


Таблицы этапа 2 (создаются заранее или позже):

agent_logs  — id, agent, action, item_id, reason, created_at
matches     — id, lost_item_id, found_item_id, score, created_at


Хранилище фото: бакет item-images.

## 11. Безопасность и приватность

- Row Level Security включена на всех таблицах:
  - читать видимые объявления может любой посетитель
  - создавать объявления может только вошедший пользователь, user_id равен его id
  - изменять и удалять объявление может автор, скрывать может модератор, удалять любое может администратор
  - менять роли может только администратор
- Ключи хранятся в .env.local, файл не попадает в Git; в Vercel ключи задаются в настройках проекта
- Telegram-ник виден всем посетителям: при публикации показывается предупреждение, что контакт публичный
- Ввод проверяется на клиенте и ограничениями в базе
- Агенты (этап 2) работают только через отдельные сервисные аккаунты с ограниченными правами

## 12. Нефункциональные требования

- Адаптивность: корректный вид от 360 px
- Скорость: лента открывается быстро (загрузка страницами по 12-20 объявлений)
- Доступность: читаемый контраст, подписи у кнопок и полей
- Поддержка актуальных Chrome, Firefox, Safari, Edge
- Понятные сообщения для пустой ленты, ошибок формы и сбоев сети

## 13. Технические требования

- Next.js (App Router), TypeScript
- Tailwind CSS
- Supabase: PostgreSQL, Auth, Storage, RLS
- @supabase/supabase-js
- Git и GitHub, деплой на Vercel
- Для этапа 2: доступ к LLM API (ключ хранится только на сервере, никогда в браузере)

## 14. Команда и распределение ролей (4 человека)

Имена заполняет команда. Если в команде меньше разработчиков, роли объединяются.

| Участник | Роль в проекте | Ответственность | Основные файлы и области |
|---|---|---|---|
| ____ | Руководитель проекта и интеграция | Координация, ТЗ, README, слияние изменений, проверка перед сдачей, деплой на Vercel | TZ.md, README.md, настройки репозитория |
| ____ | Backend и безопасность | Проект Supabase, таблицы, RLS, Auth, Storage, роли | SQL, lib/supabase, .env.local |
| ____ | Frontend: данные и логика | Лента, фильтры, поиск, форма, страница объявления, модерация | app/, components/, lib/ |
| ____ | Frontend: дизайн и качество | Дизайн, адаптивность, состояния загрузки и ошибок, тестирование | globals.css, компоненты UI, чек-лист тестов |

Правила командной работы:
- Каждый работает в своей ветке (feature/<название>), напрямую в main не пишет
- Перед началом работы и перед отправкой всегда git pull
- Слияние в main через Pull Request, проверяет руководитель проекта
- Осмысленные сообщения коммитов
- Ключи и пароли никогда не коммитятся

## 15. Этапы выполнения

1. *Подготовка:* репозиторий, Next.js, README, структура папок, ветки (все)
2. *Supabase:* проект, таблицы, RLS, бакет для фото, ключи (Backend)
3. *Авторизация и роли:* вход, регистрация, profiles (Backend и Frontend: логика)
4. *Лента и карточки* (Frontend: логика, дизайн)
5. *Форма и загрузка фото* (Frontend: логика)
6. *Фильтры и поиск* (Frontend: логика)
7. *Страница объявления, статусы, жалобы, /my* (Frontend: логика)
8. *Модерация и админка* (Backend и Frontend: логика)
9. *Дизайн и адаптивность* (Frontend: дизайн)
10. *Тестирование, README, деплой* (руководитель, все)
11. *Этап 2 (после защиты):* агенты по очереди: модератор, сопоставитель, координатор, помощник

## 16. Риски

| Риск | Что делать |
|---|---|
| Конфликты в Git между четырьмя людьми | Ветки, pull перед работой, Pull Request |
| Утечка ключей в репозиторий | .env.local в .gitignore, проверка git status перед коммитом |
| Неправильная RLS: чужие данные доступны или удаляются | Тестировать под тремя ролями, не только в интерфейсе |
| Проект слишком большой | Строго держаться MVP, этап 2 не начинать до сдачи |
| Агент ошибается (ложный спам, неверное совпадение) | Только подсказки и пометки, решение за человеком |
| Расходы на LLM API | Лимиты запросов, проверка только новых объявлений |
| Публичный Telegram-ник | Предупреждение при публикации |

## 18. Монетизация (концепция)

Партнёрство с университетами и организациями: брендированная версия для кампуса, статистика возвратов для администрации. В учебной версии не реализуется.

## 19. Критерии готовности

- Пользователь может зарегистрироваться, войти и выйти
- Объявление с фото видят все посетители
- Автор меняет статус и удаляет только свои объявления (проверено через интерфейс и политиками RLS)
- Модератор может скрыть объявление и закрыть жалобу, обычный пользователь не может
- Администратор может назначить роль
- Фильтры и поиск работают вместе
- Сайт нормально выглядит на телефоне и компьютере
- Ключи не попали в репозиторий
- Проект задеплоен и доступен по ссылке
- В README описаны запуск, переменные окружения, структура и роли команды
- В TZ.md заполнены имена участников
